# magpie-persona-gen

Synthetic multi-turn conversation generator for SFT fine-tuning, with regional persona injection. It is inspired by Magpie ([Xu et al., arXiv:2406.08464](https://arxiv.org/abs/2406.08464)), which synthesizes alignment data by letting an aligned LLM generate both sides of a conversation, but it does not implement the original Magpie trick.

## How it works

Magpie prompts an aligned model with only the chat-template prefix up to the user role header, so the model completes a user turn on its own. This project does not do that. Instead, a single vLLM model plays both roles through `llm.chat()`, and each role gets an explicit system prompt:

- **Simulated user (interviewer).** The system prompt describes a human chatting with an AI assistant. It is filled in with a persona (a text profile from `data/personas/<country>/`, truncated to 600 characters), a personality drawn from the scenario, and the scenario objective. On the first turn, the scenario's `first_turn_hint` is appended. The prompt contains no assistant knowledge.
- **Assistant (responder).** The system prompt is the language-specific file `config/system_prompt_<lang>.txt`, with `{curriculum}` replaced by a scenario-specific knowledge excerpt from `config/curricula/`. The assistant only sees the curriculum, not the persona.

Both roles are generated by the same model with different system prompts and sampling settings. The loop alternates between them for a random number of turns per conversation (between `--turns-min` and `--turns-max`), and the finished conversations go through a separate quality filter and a two-pass deduplication.

Differences from the original Magpie method:

- Generation uses chat messages with system prompts, not a raw template prefix.
- User turns are conditioned on a persona, a personality and a scenario objective, rather than being sampled unconditionally.
- The assistant is grounded on a curriculum excerpt and instructed to say it does not know when the information is not in it.
- Scenarios are sampled by weight, and conversations are filtered and deduplicated afterwards.

## Pipeline

```
  data/personas/<country>/*.txt         config.py SCENARIOS (weighted)     config/curricula/*.txt
              |                                      |                              |
              +---------- sample persona ------------+---- sample scenario --------+
                                      |
                         build interviewer + responder system prompts
                                      |
        +---------------------------- turn loop (per conversation) ----------------------------+
        |   simulated user: llm.chat([system(persona, personality, objective), history])        |
        |        -> drop conversation if the message is invalid or in the wrong language        |
        |   assistant:      llm.chat([system(curriculum), history, user message])               |
        |        -> drop conversation if the answer is empty (< 5 chars)                        |
        +---------------------------------------------------------------------------------------+
                                      |
                 run.py   -> raw JSONL     (messages + metadata)
                                      |
                 filter.py -> clean JSONL  (rule-based checks)
                                      |
                 dedup.py  -> deduped JSONL (exact on first user message, then MinHash LSH)
                                      |
                 upload_hf.py -> parquet (+ optional push to the HuggingFace Hub)
```

Details that matter when reading the output:

- Conversations are generated in batches of `--batch-size`. Within a batch, every active conversation advances one turn at a time so each `llm.chat()` call is batched.
- A conversation is dropped from the loop at the turn where it fails a check. If it already has at least `--turns-min` completed turns it is still saved, with `metadata.turns` set to the number of completed turns. Otherwise it is discarded, and the loop keeps generating until `--total` conversations have been saved.
- In-loop validation of the simulated user message: non-empty and at least 3 characters, not a meta line such as `[End of conversation]`, no `user > assistant` role-flow artifact, no trailing "the assistant has provided..." commentary, and, for Spanish and Portuguese, a lightweight check that the text contains language indicators.
- Language: with `--lang es` only non-Brazilian personas are used; with `--lang pt` only `brasil` personas; with `--lang en` all personas are used (persona text is not translated). Without `--lang`, Brazilian personas get Portuguese and all others Spanish. In that mixed mode the first-turn hint is still labeled as Spanish and the language check is skipped.
- Sampling: temperature 0.1 and top_p 0.95 for both roles, `max_tokens` 150 for the simulated user and 500 for the assistant (plus a repetition penalty of 1.05), with stop tokens read from the model's `generation_config` (see `config.py` and `run.py`).
- The assistant system prompt is stored as a `system` message in about 10% of saved conversations.


## Quick start

```bash
pip install -r requirements.txt

# Spanish — 500 conversations, default model
python run.py --total 500 --lang es --out data/es.jsonl

# 2-GPU run (e.g. on GPUs 1 and 2)
python run.py --total 500 --lang es --tp 2 --gpu-ids 1,2 --out data/es.jsonl

# Custom assistant name (shown to the simulated user)
python run.py --total 200 --lang es --assistant-name "MyBot" --out data/es.jsonl

# Use a different model
python run.py --total 100 --lang en --model /path/to/model --out data/en.jsonl
```

## Options

| Flag | Default | Description |
|---|---|---|
| `--total` | 100 | Number of conversations to generate |
| `--lang` | mixed | Force language: `es`, `en`, `pt` |
| `--turns-min` | 1 | Minimum turns per conversation |
| `--turns-max` | 5 | Maximum turns per conversation |
| `--batch-size` | 50 | vLLM batch size |
| `--out` | `data/conversations.jsonl` | Output JSONL path |
| `--model` | (see config.py) | Override model path |
| `--assistant-name` | `LatamGPT` | Name shown to the simulated user |
| `--tp` | 4 | Tensor parallel size (number of GPUs) |
| `--gpu-ids` | all visible | Comma-separated GPU IDs, e.g. `1,2` |

### Resume support

If a run is interrupted, re-run the exact same command. The pipeline counts existing lines in the output file and generates only what's missing:

```bash
# Run crashed at 1 267 / 20 000 — just re-run:
python run.py --total 20000 --lang es --out data/es_20k.jsonl
# → Resuming: 1267 conversations already in data/es_20k.jsonl, need 18733 more.
```

## Running all stages

```bash
# 1. Generate raw conversations
python run.py --total 5000 --lang es --out data/es_raw.jsonl

# 2. Filter for quality
python filter.py data/es_raw.jsonl --out data/es_clean.jsonl

# 3. Deduplicate
python dedup.py data/es_clean.jsonl --out data/es_dedup.jsonl

# 4. Upload to HuggingFace
huggingface-cli login
python upload_hf.py --repo-id myorg/my-dataset-es --lang es --input data/es_dedup.jsonl
```

## Outputs

| Stage | Command | Output |
|---|---|---|
| Generate | `run.py` | JSONL, one conversation per line, appended as each one finishes |
| Filter | `filter.py` | JSONL with the conversations that pass every check; prints counts per removal reason |
| Deduplicate | `dedup.py` | JSONL with exact and near duplicates removed; prints counts per pass |
| Upload | `upload_hf.py` | A parquet file next to the input JSONL (same name, `.parquet`), and, unless `--dry-run`, a private dataset repo on the Hub with `data/data.parquet` and a generated dataset card |

`filter.py` and `dedup.py` accept several input files and write a single merged output. With `--dry-run` they only print statistics. `run.py` logs to stdout and writes no file other than the JSONL.

### Raw, filtered and deduplicated JSONL

Each line is a JSON object:

```json
{
  "messages": [
    {"role": "user", "content": "¿Quién te creó?"},
    {"role": "assistant", "content": "Fui creado por CENIA..."}
  ],
  "metadata": {
    "scenario_id": "origin_story",
    "pais": "argentina",
    "language": "Spanish",
    "turns": 5
  }
}
```

The `system` message (the responder system prompt, including the curriculum) is included in ~10% of conversations so the model learns to follow it when present but does not depend on it at inference time. `metadata.language` is the full language name (`Spanish`, `Portuguese` or `English`), `metadata.pais` is the persona's country directory name, and `metadata.turns` is the number of completed user/assistant exchanges. The filtered and deduplicated files keep the same format.

### Parquet and Hub dataset

`upload_hf.py` converts each record to a row with these columns:

| Column | Source |
|---|---|
| `messages` | `messages` list of `{content, role}` |
| `hash` | SHA-256 of the first user message (not normalized, unlike the exact-dedup key in `dedup.py`) |
| `country` | `metadata.pais` |
| `language` | `metadata.language` |
| `scenario` | `metadata.scenario_id` |

## Customising the assistant profile

1. **System prompts** — edit `config/system_prompt_es.txt` (or `_en.txt` / `_pt.txt`). The `{curriculum}` placeholder is replaced at runtime with a scenario-specific excerpt.

2. **Curricula** — edit files in `config/curricula/`. Each scenario maps to one file; the content is injected into the responder's system prompt. Add, rename, or replace files freely — just update the `curriculum` key in `config.py` scenarios.

3. **Scenarios** — defined in `config.py`. Each entry has a `weight`, `curriculum`, `objective`, `first_turn_hint`, and `personalities` list. Add custom scenarios without touching the generation code.

4. **Personas** — place `.txt` files under `data/personas/<country>/`. One persona per file. Run `python build_personas.py` to refresh from the HuggingFace dataset.

## Filtering

`filter.py` removes known generation artifacts. Each conversation is checked in the order below and removed for the first check it fails:

1. Degenerate user turn: empty, first user message shorter than 8 characters, or any user message ending with `:`.
2. Role-flow or meta-commentary artifacts in user messages.
3. Assistant message starting with an apology (for example "I'm sorry", "lo siento").
4. Assistant message shorter than 30 characters.
5. Identity scenarios (`casual_discovery`, `direct_identity`, `origin_story`) where the assistant never mentions an identity term.
6. Generic "as an AI" phrasing in an assistant message.
7. Role labels echoed inside a message (for example a line starting with `assistant:`).
8. Markdown bullet lists in assistant messages for Spanish and Portuguese conversations.

For identity scenarios, the terms are configurable:

```bash
# Default terms: "latamgpt,cenia"
python filter.py data/es_raw.jsonl --out data/es_clean.jsonl

# Custom terms for a different assistant
python filter.py data/es_raw.jsonl --out data/es_clean.jsonl --identity-terms "mybot,myorg"
```

## Uploading to HuggingFace

`--repo-id` is required (no default to avoid accidental uploads):

```bash
python upload_hf.py --repo-id org/my-dataset-es --lang es
python upload_hf.py --repo-id org/my-dataset-es --lang es --description "LatamGPT self-identity SFT"
python upload_hf.py --repo-id org/my-dataset-es --lang es --dry-run   # local parquet only
```

## Deduplication

`dedup.py` runs two passes, keeping the first occurrence in input order:

1. Exact: SHA-256 of the normalized (lowercased, whitespace-collapsed) first user message.
2. Near: MinHash LSH over character 5-grams of the full user and assistant text. `--threshold` (default 0.80) is the Jaccard similarity cutoff and `--num-perm` (default 128) the number of permutations.

## Model requirements

Any instruction-tuned model served via vLLM with a chat template. The same model generates both the simulated user and the assistant turns, so it works best with a chat-tuned model that follows system-prompt instructions reliably.

Default: `Llama-3.1-70B-LatamGPT-SFT-1.0` with 4-GPU tensor parallelism.
